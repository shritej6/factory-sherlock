# Seed data

Factory Sherlock has two layers of seed data: reference data that every environment needs, and a demo scenario generated by the simulation engine. Both are applied by `backend/app/seed.py`; the reference rows come from `database/seeds/01_reference_data.sql` so that the SQL a reviewer reads is the SQL that runs.

## 1. Reference data (`database/seeds/01_reference_data.sql`)

Every statement is `INSERT ... ON DUPLICATE KEY UPDATE` keyed on the natural unique column, so the file can be rerun without creating duplicates. `seed.py` strips comment lines, splits the file on semicolons, and executes each statement through the session.

| code | name | description |
|------|------|-------------|
| OVERSIZE_DIAMETER | Oversized diameter | Measured diameter above the upper tolerance limit |
| UNDERSIZE_DIAMETER | Undersized diameter | Measured diameter below the lower tolerance limit |

`backend/app/domain/quality_rules.py` maps a failed measurement to one of these codes: diameter characteristics (`diameter`, `outer_diameter`, `bore_diameter`) give `OVERSIZE_DIAMETER` or `UNDERSIZE_DIAMETER` by the sign of the deviation, `hole_position` gives `HOLE_POSITION_DEVIATION`, anything else gives `DIMENSIONAL_DEVIATION`. `SURFACE_DAMAGE` is added by the simulation for gross material defects.

## 2. Demo scenario (`database/seeds/demo_scenario.json`)

`python -m app.seed --demo` loads this file, drops its `description` key, validates it as a `SimulationRequest`, and runs `simulation_service.run_simulation` in the same transaction as the reference data.

```json
{
  "seed": 42,
  "start_time": "2026-11-02T06:00:00",
  "batches_per_machine": 12,
  "units_per_batch": 20,
  "minutes_per_batch": 30,
  "faults": [
    { "machine_code": "CNC-03", "fault": "TOOL_WEAR", "start_batch_index": 4 },
    { "machine_code": "CNC-02", "fault": "DOWNTIME", "start_batch_index": 6 }
  ]
}
```

### How the scenario becomes rows

- Machines are processed in code order and each is dedicated to one product in product-code order: CNC-01 makes GEAR, CNC-02 makes METAL-BRACKET, CNC-03 makes STEEL-SHAFT.
- Every four batches (`batches_per_order = 4`, a `SimulationConfig` default) form one order of 80 planned units, so 12 batch slots per machine give 3 orders per machine and 9 orders in total. Orders are numbered `SIM0001-<machine>-<nn>`; the run tag is derived from the number of existing orders, so a second run on a populated database gets a different tag.
- Each batch is 30 minutes long and contains 20 units; each unit is inspected on both of its product's characteristics, giving 40 inspections per batch.
- Lots rotate: batch index `i` uses the product's lot number `(i // 2) % 3`, and every third batch (`i % 3 == 2`) also draws from the next lot, so consecutive batches share lots and traceability has something to find.
- `TOOL_WEAR` on CNC-03 starts at batch index 4 (08:00): a `TOOL_WEAR` event and a `RUNNING` to `WARNING` state change are recorded, and the primary characteristic (shaft diameter) drifts upward by 0.8 percent of tolerance per unit produced.
- `DOWNTIME` on CNC-02 at batch index 6 (09:00): the machine goes `RUNNING` to `FAULT` to `STOPPED` to `IDLE` to `RUNNING` over 30 minutes, a `DOWNTIME` event and a `MACHINE_FAULT` alert are recorded, and that batch slot is lost. The order containing the slot therefore ends with 3 batches and 60 of 80 units and stays `IN_PROGRESS`.
- A `HIGH_DEFECT_RATE` alert is raised when a batch's failure rate reaches 0.15 and the previous batch did not already raise one.
- Machines with an unresolved fault finish in `WARNING`; others return to `IDLE`.

Other facts about the seeded state:

- Production spans 2026-11-02 06:00:00 to 12:00:00; inspection timestamps run from 06:01:30 to 12:00:00.
- Final machine statuses: CNC-01 `IDLE`, CNC-02 `IDLE`, CNC-03 `WARNING`.
- Order statuses: 8 `COMPLETED`, 1 `IN_PROGRESS` (`SIM0001-CNC-02-02`, 60 of 80). All orders have `due_date = 2026-11-02`.
- The two alerts read "CNC-02 entered FAULT during simulated downtime" and "Batch 10 on CNC-03 failed 25% of inspections".
- The machine events on CNC-03 are: `STATE_CHANGE IDLE->RUNNING` at 06:00 ("Simulation started"), `STATE_CHANGE RUNNING->WARNING` at 08:00 and `TOOL_WEAR` at 08:00 (both "Simulated cutting tool wear: dimensions drift upward over time"). There is no closing state change because the machine remains in `WARNING`.

The hourly defect-rate profile on CNC-03 that results from this scenario, and the batches that cross the review threshold, are shown as real query output in [queries.md](queries.md).

## 3. Resetting the database

```sh
cd backend
uv run python ../scripts/development/reset_database.py --demo
```

`scripts/development/reset_database.py`:

1. Reflects every table in the configured database, disables `FOREIGN_KEY_CHECKS`, drops them all, and re-enables the checks. It touches only tables, never users or privileges.
2. Runs `uv run alembic upgrade head` in `backend/` to recreate the schema from `backend/migrations/versions/`.
3. Runs `uv run python -m app.seed`, with `--demo` when requested.

With `APP_ENV=test` the script operates on `factory_sherlock_test` instead, which is how the test suite keeps development data untouched. Without `--demo`, only the reference data and the four accounts are created; the demo scenario (or any other scenario) can then be generated through `POST /simulation/runs` by an engineer or admin.
