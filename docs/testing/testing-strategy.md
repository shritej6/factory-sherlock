# Testing strategy

This document defines how Factory Sherlock is tested: the shape of the test pyramid for this repository, the test categories, how the test database is isolated, and where each of the twelve required scenarios from the project brief lives. The backend tests under `backend/tests/` and the frontend tests under `frontend/src/**/*.test.ts(x)` exist; this document describes the strategy and where each scenario is tested. The last full local `uv run pytest --cov=app` run (2026-11-07) reported 279 passed with 97 percent line coverage of `app`; the frontend suite last ran on 2026-11-03 (`pnpm test`: 13 files, 39 tests, all passing). Per-scenario results are recorded in [test-matrix.md](test-matrix.md).

Tooling: `pytest` with `pytest-cov` and `httpx` (FastAPI `TestClient`) for the backend (`backend/pyproject.toml`, dev dependency group); Vitest with Testing Library and jsdom for the frontend (`frontend/vite.config.ts`, `frontend/tests/setup.ts`). The pytest marker `integration` is declared for tests that need a running MySQL test database; `backend/tests/conftest.py` adds it automatically to everything under `tests/api` and `tests/integration`.

Current layout: 6 unit modules, 10 API modules, and 3 integration modules (158 test functions; 279 test cases with parametrisation, of which 144 are unit cases and 135 need MySQL), plus 13 frontend test files. Browser-driven end-to-end tests are planned and not yet written.

## Test pyramid for this repository

The code base has a thick domain and simulation layer that is deliberately free of I/O, a thin API layer, and a set of behaviours that only exist in MySQL (constraints, window functions, LATERAL joins, ROLLUP). The pyramid follows that shape.

| Level | Share of tests (target) | What it covers | Needs MySQL |
|-------|-------------------------|----------------|-------------|
| Unit | about 70 percent | `domain/quality_rules.py`, `domain/state_machines.py`, `simulation/*` (engine, faults, measurement, state tracker, config validation), `investigation/rules.py` and `summary.py` with a fake `QueryRunner`, `core/security.py`, `repositories/sql_loader.py` catalogue naming, Pydantic schema validation. | No |
| Integration (API and database) | about 20 percent | Route handlers through `TestClient` against the test database: authentication and roles, order and batch workflows, inspections, quarantine cascade, investigation creation, simulation persistence, constraint violations, error response shapes; the SQL files executed against seeded data. | Yes |
| End-to-end | about 10 percent (target; none written yet) | The demo scenario from seed to investigation to quarantine through the API, and browser flows against the frontend. | Yes |

Unit tests run without any environment; the engine in `core/database.py` is created at import time but does not connect until a session is used, so importing `app` modules in unit tests is safe as long as `.env` or environment variables provide a parsable configuration.

## Test categories

### Unit tests (`backend/tests/unit/`)

- Quality rules: boundary of `abs(measured - target) <= tolerance` (exactly on the limit passes), classification by characteristic and sign, `defect_rate` rounding and the zero-inspection case.
- Quality rules, continued: `test_classification_covers_every_characteristic_and_sign` covers `bore_diameter`, `outer_diameter`, `length`, `thickness`, and `hole_position` with the sign of the deviation; `test_tolerance_boundary_is_inclusive_on_both_sides` pins the lower limit.
- State machines: every pair of states in `MACHINE_TRANSITIONS`, `ORDER_TRANSITIONS`, `BATCH_TRANSITIONS`, and `INVESTIGATION_TRANSITIONS` is compared with the tables in BR-20, BR-34, BR-56, and BR-74 (`test_every_*_edge_matches_the_documented_table`, 64 cases): allowed edges pass and every other edge raises `InvalidTransitionError` with status 422 and `details.current`, `details.target`, and `details.allowed`; terminal states reject everything.
- Simulation: `SimulationConfig` and `Catalog` invariants (`test_catalog_and_config_invariants_are_enforced`); `SimulationEngine` determinism (same seed equals, different seed differs), batch and unit counts, order grouping, DOWNTIME slot loss and state sequence, the stored machine state as the starting point, final machine states; `test_high_defect_rate_alert_is_raised_once_per_consecutive_run` asserts exactly one `HIGH_DEFECT_RATE` alert for a `TOOL_WEAR` run, naming the first batch at or above 0.15. `combined_effect` and `MeasurementGenerator` are covered through the engine, not by their own tests (`faults.py` 91 percent, `measurement.py` 85 percent).
- Investigation: each rule against a fake runner returning canned rows, including the `None` paths (R2 with no defects, R3 and R4 without a machine, R4 without onset, R6 without batches); context propagation between rules; `test_elevation_threshold_boundaries` (0.05 and twice the fleet rate, five cases), `test_onset_is_the_first_bucket_at_or_above_ten_percent` (also checks the parameters R4 and R5 receive), `test_no_onset_skips_the_event_rule_and_says_so`; `build_summary` wording for elevated and non-elevated cases; `test_narratives_and_summary_never_assert_causation` checks every narrative and the summary against a list of causal words.
- Security: hash and verify round trip, malformed hash returns false, token encode and decode, expired token raises `AuthenticationError`.
- Schemas (`tests/unit/test_schemas.py`): `extra="forbid"`, the code pattern, and every numeric and length limit named in BR-10, BR-12, BR-14, BR-23, BR-31, BR-51, BR-52, BR-65, BR-70, BR-71, BR-82, BR-90, and BR-91, each with a value just inside and one just outside the limit.
- SQL loader: file stem to name mapping (`01_...` prefix removed, subdirectory dotted), unknown name raises `UnknownQueryError`.

### API tests (`backend/tests/api/`)

Run with `TestClient(app)` against the test database. A session-scoped fixture runs `alembic upgrade head` on the test database (and refuses to run unless the effective database name ends with `_test`); a per-test fixture truncates every table, applies the reference seed, and creates the demo users. Login fixtures obtain tokens for the engineer, operator, and viewer accounts.

- Authentication and authorisation: 401 without or with an invalid token; 403 for roles outside the allowed set on every engineer-only route (10 routes, operator and viewer) and every operator-set route (6 routes, viewer), with the operator admitted to the latter; the database row decides the role, not the token (`test_the_database_role_decides_not_the_token`); a deactivated user is rejected immediately (`test_deactivated_users_lose_access_immediately`).
- Error contract (`tests/api/test_error_contract.py`): every error body has exactly the `ErrorResponse` keys `error`, `message`, `details`, and `request_id`, the 12-character `request_id` equals the `X-Request-ID` header, and no body contains "Traceback", "SELECT", "pymysql", or "sqlalchemy". 422 bodies carry `details.errors[]` with `field` and `message`. The 500 body is produced by raising `RuntimeError` inside a service for one request with `TestClient(app, raise_server_exceptions=False)`; the exception text never reaches the client. The 503 body is produced by pointing `app.core.database.SessionLocal` at a port with no listener, so the first query raises `OperationalError` 2003, which `handle_operational` maps to 503 `DatabaseUnavailable` for `GET /health` and for a protected route. The remaining branches of `app/api/errors.py` are driven with constructed driver errors: lock wait timeout and deadlock (1205, 1213) give 409, a foreign key violation (1452) gives 422, and any other `IntegrityError` gives 500 "The request violated a database rule". `app/api/errors.py` is at 100 percent line coverage.
- Resource endpoints: create, read, list, update, status change for products, machines, material lots, orders, batches, inspections, investigations, alerts; traceability forward and backward; simulation runs. Service-level business rules are checked with one rejection and one boundary case each (see Business rule tests below).

### Database integration tests (`backend/tests/integration/`, marker `integration`)

- Constraints (`test_transactions.py`): UNIQUE (usernames, emails, codes, lot numbers, characteristics, defect codes, serial numbers, batch sequences, batch-lot pairs, evidence sequences), CHECK, and ENUM rejections observed as `IntegrityError`, `OperationalError`, or `DataError` when writing raw rows without the service checks; the service-level completion guard (`complete_batch` raises `ConflictError` before `ck_order_completed_within_planned` fires).
- Foreign keys (`test_foreign_keys.py`): every `ON DELETE` rule in the migration, exercised with raw `DELETE` statements so MySQL is observed rather than the ORM cascade settings. RESTRICT: product with orders, material lot with batch links, machine with batches or events, order with batches, batch with units or material links or investigation links, defect type in use, inspected unit, and an inspection referencing a missing specification. CASCADE: product to specifications, inspection to defect links, investigation to evidence and batch links. SET NULL: machine on alerts, investigations, and orders; user on `alerts.acknowledged_by` and `investigations.opened_by`; product on `investigations.product_id`. Each RESTRICT test re-reads the row from a fresh session to show it survived. Note that the batch delete is RESTRICT, not CASCADE, on all three child tables; BR-58 in `docs/requirements/business-rules.md` describes CASCADE and needs correcting.
- Transactions: a failure in the middle of `create_batch` (`test_batch_with_unavailable_lot_leaves_nothing_behind`), `quarantine_lot` (`test_lot_quarantine_rolls_back_completely_when_the_alert_insert_fails`), or `persist` (`test_failed_persistence_leaves_no_simulated_rows`) leaves no partial rows. The last two force a duplicate-key `IntegrityError` on the alert insert, which is the final write of each service, and read the lot, batch, order, and alert tables back afterwards.
- SQL files: `test_all_queries_run_and_agree` executes each of the twelve queries against the simulated data and asserts the key columns and cross-query agreement (for example the failed count equals the simulation result and `order_completion_summary` has an `ALL`/`ALL` row); the SQL catalogue completeness check is in `tests/unit/test_security_and_loader.py`.

### Simulation tests

Unit tests on the engine as listed above, plus two API tests in `tests/api/test_simulation_api.py`: `test_simulation_is_deterministic_across_runs` posts the same request twice and compares the failed inspection counts; `test_same_seed_reproduces_every_measured_value_and_result_per_serial` posts a 30-unit scenario with seed 99 twice and seed 100 once, reads every unit back through `GET /traceability/backward/{serial}`, and compares sorted (serial without the run tag, `inspection_summary`) tuples, where `inspection_summary` carries `measured_value` and `result` per characteristic. The seed-99 lists are equal; the seed-100 list has the same serials and different values. `test_simulation_refuses_to_run_without_available_lots` quarantines every GEAR lot and asserts the 422 from `load_catalog`; `test_failed_persistence_leaves_no_simulated_rows` covers the persistence transaction.

### Investigation tests

Unit tests with a fake runner (`tests/unit/test_investigation_rules.py`), plus API tests (`tests/api/test_investigations_api.py`) that run the small simulated scenario, open an investigation for CNC-03, and assert structural properties: cards R1 to R6 present in that order, the summary mentions an elevated rate, the oversize diameter and `TOOL_WEAR`, the first card carries the SQL of query 01 and a CNC-03 row, the R4 card lists the `TOOL_WEAR` event, a healthy machine is not flagged, and stored evidence rows keep the SQL column order. `test_every_flagged_batch_comes_from_r5_and_is_linked_in_the_database` asserts that the set of `batch_links` equals the set of `batch_id` values in the R5 card rows, that every link carries the reason "Defect rate above review threshold", that the `investigation_batches` rows match, and that `batches_requiring_review` then reports those batches with `already_under_investigation` 1. `test_every_evidence_card_stores_the_exact_sql_file_and_ordered_columns` asserts that each card's `query_sql` equals `load_sql(query_name)` both in the response and in the stored row, that sequences run 1 to n, and that the stored `{"columns", "rows"}` payload matches the response rows in order. `test_investigation_window_and_title_boundaries` and `test_investigation_can_be_reopened_from_review_but_not_after_closing` cover BR-70, BR-71, BR-74, and BR-75 at the API.

### End-to-end tests

No end-to-end test has been written. The intended flow is: seed, run the demo simulation, read alerts, open the investigation, quarantine the worst batch, confirm it disappears from `batches_requiring_review`, close the investigation with a conclusion, verify `CLOSED` is terminal. Pieces of it are covered separately by API tests. Vitest component tests render the screens against mocked fetches (login, orders role gating, traceability, evidence card, SQL explorer, SQL disclosure) together with unit tests for the HTTP client, permissions, transitions, chart transforms, and cell rendering.

## Test database isolation

`backend/app/core/config.py` computes `effective_database`: when `APP_ENV=test` the application, Alembic, and the reset script all use `<MYSQL_DATABASE>_test` (`factory_sherlock_test` with the default name). `scripts/setup/init_databases.sh` creates both schemas with identical grants for the application user, so the test suite can run migrations itself.

Running the backend tests:

```bash
cd backend
APP_ENV=test uv run alembic upgrade head     # once, or let the fixture do it
APP_ENV=test uv run pytest                   # unit + API + integration
APP_ENV=test uv run pytest -m "not integration"
APP_ENV=test uv run pytest --cov=app --cov-report=term-missing
```

Rules:

- Tests must never run with `APP_ENV=development`; `conftest.py` sets `APP_ENV=test` before importing the application, and the migration fixture asserts that the effective database name ends with `_test`.
- The test schema is reset by `uv run python ../scripts/development/reset_database.py` with `APP_ENV=test` when a clean slate is needed.
- Unit tests do not open sessions; API and integration tests truncate every table before each test, so they must not run concurrently against the same test database.
- The seed command's demo accounts need `SEED_DEMO_PASSWORD`; the test fixture creates users directly with `hash_password` so no secret is read from the environment (`TEST_PASSWORD` in `tests/conftest.py`).

Frontend tests run with `pnpm test` (Vitest, jsdom, `src/**/*.test.{ts,tsx}`) and do not need the backend. `pnpm lint`, `pnpm typecheck`, and `pnpm build` also pass.

## Coverage and quality gates

- Target line coverage for `backend/app` of 80 percent with the domain, simulation, and investigation packages at or near 100 percent, since they are pure and cheap to cover. The run on 2026-11-07 measured 97 percent for `app` overall (2172 statements, 74 missed). Files below 90 percent: `app/seed.py` (57 percent; the command-line entry point is not run by the tests), `app/core/logging.py` (64 percent), `app/services/catalog_service.py` (86 percent), `app/api/routes/catalog.py` (88 percent), and `app/simulation/measurement.py` (85 percent). `domain`, `investigation/engine.py`, `investigation/summary.py`, `api/errors.py`, every model module, and every schema module except `schemas/investigation.py` (98 percent) are at 100 percent.
- `uv run ruff check .`, `uv run ruff format --check .`, and `uv run mypy app` pass before any test run is considered green.
- Flaky tests are fixed or deleted, not skipped. Tests that depend on random simulation outcomes must assert properties that hold for every seed (counts, ordering, structure) or pin a seed and compute the expectation from the formulas.
- Continuous integration is defined in `.github/workflows/`: `backend-ci.yml` (MySQL 8.4 service, Ruff check and format, blocking mypy, migrations, pytest with coverage), `frontend-ci.yml` (lint, typecheck, test, build), and `docs-lint.yml` (forbidden characters). All three workflows passed on the first push to GitHub on 2026-11-04 (Backend CI run 41779775539, Frontend CI run 41779775057, Docs Lint run 41779775596; https://github.com/shritej6/factory-sherlock/actions); the commands above are also run locally before each commit.
