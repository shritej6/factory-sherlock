# Testing strategy

This document defines how Factory Sherlock is tested: the shape of the test pyramid for this repository, the test categories and where each behaviour is tested, the test databases, the browser layer, what continuous integration runs, the two benchmark scripts, the coverage figures, and the gaps. Per-scenario results are recorded in [test-matrix.md](test-matrix.md).

Figures in this document were observed on 2026-11-07 in an integration worktree at commit c978744 against the database `fs_w07_test`:

- `cd backend && uv run pytest -q -p no:cacheprovider` printed `481 passed, 1 warning in 226.20s (0:03:46)`. The warning is Starlette's deprecation notice for `httpx` in `TestClient`.
- `uv run pytest --cov=app --cov-report=term -q -p no:cacheprovider` printed `TOTAL 3030 71 98%` and `481 passed, 1 warning in 221.38s (0:03:41)`.
- `uv run pytest --collect-only -q` listed 481 cases: 254 under `tests/unit`, 174 under `tests/api`, 53 under `tests/integration`, from 308 test functions in 35 modules (13 unit, 16 API, 6 integration).
- `cd frontend && pnpm -s test` printed `Test Files  25 passed (25)` and `Tests  118 passed (118)`; `pnpm -s build` finished with `built in 1.04s`.
- `frontend/e2e/` holds 5 spec files with 9 `test(` calls. The Playwright suite was not run by this pass (see End-to-end tests).

Tooling: `pytest` with `pytest-cov` and `httpx` (FastAPI `TestClient`) for the backend (`backend/pyproject.toml`, dev dependency group; `testpaths = ["tests"]`, marker `integration` declared); Vitest with Testing Library and jsdom for the frontend (`frontend/vite.config.ts` `test` block, `frontend/tests/setup.ts`, fixtures under `frontend/tests/fixtures/`); Playwright Test for the browser suite (`frontend/playwright.config.ts`). `backend/tests/conftest.py` adds the `integration` marker automatically to everything under `tests/api` and `tests/integration`.

## Test pyramid for this repository

The code base has a thick domain, simulation, and investigation layer that is free of I/O, a thin API layer, a set of behaviours that only exist in MySQL (constraints, window functions, LATERAL joins, ROLLUP, locking reads), and a React interface. The pyramid follows that shape.

| Level | Target share | Observed on 2026-11-07 | What it covers | Needs |
|-------|--------------|------------------------|----------------|-------|
| Unit | about 70 percent | 372 of 608 automated tests (61 percent): 254 backend cases plus 118 Vitest tests | Backend: `domain/quality_rules.py`, `domain/state_machines.py`, `simulation/*`, `investigation/rules.py` and `summary.py` with a fake `QueryRunner`, `core/security.py`, `core/throttle.py`, `api/errors.py` classifiers, `api/body_limit.py`, `services/inspection_csv.py`, `services/alert_service.py` rules, `core/logging.py`, `repositories/sql_loader.py`, Pydantic schemas. Frontend: components and pages rendered against mocked `fetch`, plus the HTTP client, permissions, transitions, chart transforms, formatting, and cell rendering helpers | Nothing (backend unit tests import `app` but open no session; Vitest runs in jsdom) |
| Integration (API and database) | about 20 percent | 227 of 608 (37 percent): 174 API cases and 53 database cases | Route handlers through `TestClient` against the test database (authentication and roles, every workflow, pagination, status filters, import, overdue check, throttle, error contract); the 14 SQL files against simulated data; constraints, foreign keys, indexes, transactions, locking reads, and the scheduled job | MySQL 8.4 with a `<MYSQL_DATABASE>_test` schema |
| End-to-end | about 10 percent | 9 of 608 (1.5 percent) | Login, role gating, an investigation from opening to closing, forward and backward traceability with a lot quarantine, the SQL explorer, in Chromium against the real stack | MySQL with the demo scenario, the backend, Vite, and the Playwright Chromium build |

The middle layer is larger than the target because the behaviours that matter most to this project (constraint enforcement, query correctness, transaction boundaries, the ordering of paged lists) have no unit-level substitute, and because each API module tests the service rule and its HTTP contract in one place. The browser layer is deliberately small: it checks that the screens are wired to the real backend, not that every rule holds, which the API tests already do.

## Test categories

### Unit tests (`backend/tests/unit/`, 13 modules, 254 cases)

- Quality rules (`test_quality_rules.py`, 15 cases): boundary of `abs(measured - target) <= tolerance` (exactly on the limit passes, `test_tolerance_boundary_is_inclusive_on_both_sides`), classification by characteristic and sign (`test_classification_covers_every_characteristic_and_sign` covers `bore_diameter`, `outer_diameter`, `length`, `thickness`, `hole_position`), `defect_rate` rounding and the zero-inspection case.
- State machines (`test_state_machines.py`, 79 cases): every pair of states in `MACHINE_TRANSITIONS` (25), `ORDER_TRANSITIONS` (25), `BATCH_TRANSITIONS` (9), and `INVESTIGATION_TRANSITIONS` (9) is compared with the tables in BR-20, BR-34, BR-56, and BR-74 (`test_every_*_edge_matches_the_documented_table`): allowed edges pass and every other edge raises `InvalidTransitionError` with status 422 and `details.current`, `details.target`, and `details.allowed`; terminal states reject everything; FAULT must go through STOPPED.
- Simulation (`test_simulation_engine.py`, 12 cases): `SimulationConfig` and `Catalog` invariants, determinism (same seed equal, different seed differs), batch and unit counts, order grouping, DOWNTIME slot loss and state sequence, the stored machine state as the starting point, final machine states, and exactly one `HIGH_DEFECT_RATE` alert per consecutive run at or above 0.15 (`test_high_defect_rate_alert_is_raised_once_per_consecutive_run`). `combined_effect` and `MeasurementGenerator` are covered through the engine (`faults.py` 94 percent, `measurement.py` 100 percent).
- Investigation (`test_investigation_rules.py`, 25 cases): each rule against a fake runner returning canned rows, including the `None` paths (R2 with no defects, R3 and R4 without a machine, R4 without onset, R6 without batches, R7 without a machine or with fewer than three hours); context propagation between rules (R5 batch ids reach R6, the R3 onset reaches R4 and R7); `test_elevation_threshold_boundaries` (0.05 and twice the fleet rate, five cases); `test_onset_is_the_first_bucket_at_or_above_ten_percent`; the CUSUM rule R7 (allowance 0.025, a step change signals, flat noise does not, a hand-computed example `[0.0, 0.0, 0.0, 0.055, 0.21]`, the narrative compares with the R3 onset); `test_hours_apart_counts_whole_hours_in_either_direction`; `build_summary` wording; `test_narratives_and_summary_never_assert_causation` and `test_cusum_narrative_never_uses_causal_language` check every narrative against a list of causal words.
- Security and loader (`test_security_and_loader.py`, 3 cases): hash and verify round trip and malformed hashes; token encode, decode, and tampering; the SQL catalogue names exactly the 14 documented files.
- Schemas (`test_schemas.py`, 15 tests, 24 cases): `extra="forbid"`, the code pattern, every numeric and length limit named in BR-10, BR-12, BR-14, BR-23, BR-31, BR-51, BR-52, BR-65, BR-70, BR-71, BR-82, BR-90, and BR-91 with a value just inside and one just outside; `OrderStatusCounts` has one field per `OrderStatus`.
- Alert rules (`test_alert_rules.py`, 11 cases): `days_late` counts whole calendar days and ignores the time of day; WARNING for 1 to 2 days and CRITICAL from day 3; the message text; COMPLETED and CANCELLED are never overdue.
- Inspection CSV (`test_inspection_csv.py`, 35 cases): parsing without a database, as listed in TM-22 (header handling, every rejected `measured_value` form, three-place storage, timestamps, defect codes, duplicates, the 5000-row limit, upper-cased serials, quoted fields spanning lines, broken CSV structure, truncated header echoes).
- Body limit (`test_body_limit.py`, 5 cases): `BodySizeLimitMiddleware` on a standalone app, including the ASGI-level test that cuts the application off on the third chunk.
- Login throttle (`test_login_throttle.py`, 16 tests, 21 cases): a pinned `clock.now`, the sliding window, retry-after, the pending reservation under concurrency (20 threads, 5 admitted), abandoned reservations, the `None` address, `normalise_username`, `account_key`.
- Error mapping (`test_error_mapping.py`, 19 cases): `classify_integrity`, `classify_operational`, and `classify_data` over the full errno table with pymysql-style driver errors.
- Logging formatter (`test_logging_formatter.py`, 3 cases): only allowlisted fields (`request_id`, `user_id`, `operation`, `error`, `status`, `retry_after_seconds`) reach the JSON line, `None` is omitted, exceptions are rendered.
- Catalog conflict (`test_catalog_conflict.py`, 2 cases): only MySQL 1062 becomes a 409; other integrity errors are left to the API handlers.

### API tests (`backend/tests/api/`, 16 modules, 174 cases)

Run with `TestClient(app)` against the test database. A session-scoped fixture runs `alembic upgrade head` on the test database and refuses to run unless the effective database name ends with `_test`; a per-test fixture truncates every table with `FOREIGN_KEY_CHECKS` off, applies the reference seed, and creates the demo users with `TEST_PASSWORD`; an autouse fixture resets the process-wide login throttle before and after every test. Login fixtures obtain tokens for the engineer, operator, and viewer accounts; the `ids` fixture maps codes to ids; the `simulated` fixture persists a deterministic 24-batch scenario (seed 7, 8 batches of 30 units per machine, `TOOL_WEAR` on CNC-03 from batch index 2).

- Authentication and authorisation (`test_auth_and_errors.py`, 30 cases): 401 without or with an invalid token; 403 on every engineer-only route (10 routes, operator and viewer) and every operator-set route (6 routes, viewer), with the operator admitted to the latter; the database row decides the role (`test_the_database_role_decides_not_the_token`); a deactivated user is rejected immediately; login never reveals which part was wrong, and an unknown username gets the same 401 status and message as a wrong password (`test_unknown_user_login_takes_the_slow_path`).
- Error contract (`test_error_contract.py`, 10 cases): every error body has exactly `error`, `message`, `details`, `request_id`; the 12-character `request_id` equals `X-Request-ID`; no body contains "Traceback", "SELECT", "pymysql", or "sqlalchemy"; the 500 from a `RuntimeError` inside a service; the 503 from a session factory pointed at a closed port (`OperationalError` 2003); 1205 and 1213 give 409, 1452 gives 422, other integrity errors 500; 3819 gives 422 with the constraint name, 1406 gives 422, 1366 gives 500, 1040 gives 503 "unavailable", a pool `TimeoutError` gives 503 "not reachable". `app/api/errors.py` is at 100 percent line coverage.
- Login throttle (`test_login_throttle_api.py`, 10 cases) and request body caps (`test_body_limit_api.py`, 4 cases): see TM-20 and TM-23.
- Resource endpoints: products, machines (`test_machines_api.py`), orders (`test_orders_api.py`, 11 cases), batches (`test_batches_api.py`, 12 cases), inspections (`test_quality_api.py`, 7 cases), the CSV import (`test_inspection_import.py`, 20 cases), investigations (`test_investigations_api.py`, 8 cases, cards R1 to R7), alerts and the SQL catalogue (`test_analytics_api.py`, 8 cases), the overdue check (`test_alert_checks_api.py`, 8 cases), traceability (`test_traceability_api.py`, 6 cases), simulation runs (`test_simulation_api.py`, 7 cases). Each service-level business rule has one rejection and one boundary case (see Business rule tests).
- List contracts: the page envelope on the six list endpoints (`test_pagination_api.py`, 12 cases, including the `offset` upper bound of 1,000,000) and the repeatable `status` filters, `GET /production-orders/status-counts`, and `order_number` on batch rows with a constant statement count (`test_status_filters_api.py`, 18 cases).

### Database integration tests (`backend/tests/integration/`, 6 modules, 53 cases, marker `integration`)

- Constraints (`test_transactions.py`, 25 cases): UNIQUE (usernames, emails, codes, lot numbers, characteristics, defect codes, serial numbers, batch sequences, batch-lot pairs, evidence sequences), CHECK, and ENUM rejections observed as `IntegrityError`, `OperationalError`, or `DataError` when writing raw rows without the service checks; the batch lifecycle CHECKs; decimal precision; the atomic `complete_batch` increment; the service-level completion guard (`ConflictError` before `ck_order_completed_within_planned` fires); rollback of a failed flush and of a run whose last bulk insert fails.
- Foreign keys (`test_foreign_keys.py`, 14 cases): every `ON DELETE` rule in the first migration, exercised with raw `DELETE` statements so MySQL is observed rather than the ORM cascade settings. RESTRICT: product with orders, material lot with batch links, machine with batches or events, order with batches, batch with units or material links or investigation links, defect type in use, inspected unit, inspection referencing a missing specification. CASCADE: product to specifications, inspection to defect links, investigation to evidence and batch links. SET NULL: machine on alerts, investigations, and orders; user on `alerts.acknowledged_by` and `investigations.opened_by`; product on `investigations.product_id`. Each RESTRICT test re-reads the row from a fresh session to show it survived. The batch delete is RESTRICT on all three child tables; BR-58 says so since 2026-11-07.
- Alert to order link and the job (`test_alert_order_link.py`, 6 cases): `alerts.production_order_id` SET NULL on order delete, the link kept through acknowledgement, idempotency across sessions, two concurrent checks serialised by `SELECT ... FOR UPDATE` (a real second thread and session that blocks and then raises nothing), and `app.jobs.check_overdue_orders.main` exiting 0 with its INFO line or 1 with a rolled-back transaction and an ERROR line.
- Indexes (`test_list_ordering_indexes.py`, 2 cases): the five indexes of migration `6c1f0d2a9b47` exist with their columns in order and the implicit `specification_id` index on `inspections` is gone.
- Simulation persistence (`test_simulation_persistence.py`, 2 cases): a run spanning several 1000-row chunks persists the exact counts, and every stored inspection points at the unit with the matching serial.
- SQL files (`test_queries.py`, 4 cases): `test_all_queries_run_and_agree` executes the 14 files (ten numbered dashboard queries and the four investigation queries, including `investigation.hourly_defect_rates` through R7 in the API tests) against the simulated data and asserts key columns and cross-query agreement (the failed count equals the simulation result, `order_completion_summary` has an `ALL`/`ALL` row, the control chart returns 8 rows with the last mean above `ucl`); the three control chart tests cover the 15-column shape, per-subgroup limits that widen as `sample_count` falls, and the optional machine filter.

### Frontend component tests (`frontend/src/**/*.test.{ts,tsx}`, 25 files, 118 tests)

Vitest runs in jsdom with `globals: true`, `css: false`, and `frontend/tests/setup.ts`, which loads `jest-dom` matchers, cleans up after each test, stubs `ResizeObserver` for Recharts, and replaces Node's experimental `localStorage` with an in-memory `Storage`. Tests render components with the React Query client and router helpers in `frontend/tests/helpers.tsx` and mock `fetch` per test; `frontend/tests/fixtures/controlChart.ts` builds control chart rows with per-`sample_count` limits. Coverage by area: layout and navigation (`AppLayout.test.tsx`), shared components (`Disclosure`, `Pagination`, `SqlDisclosure`, `States`, `StatTile`, `ChartFrame`, `ControlChart`), pages and panels (`LoginPage`, `OrdersPage`, `TraceabilityPage`, `OverviewPage`, `AlertsList`, `BatchActions`, `EvidenceCard`, `SqlExplorer`, `ControlChartPanel`, `ImportInspectionsPanel`), the session (`AuthProvider.test.tsx`), the HTTP client (`http.test.ts`: error envelope to `ApiError`, network failures, 401 handling, multipart bodies, repeated query keys), and pure helpers (`chartTransforms`, `format`, `permissions`, `renderCell`, `transitions`). What they assert is listed in TM-13, TM-16, TM-20, TM-21, TM-22, TM-24, TM-25, TM-27, and TM-29. `pnpm lint`, `pnpm format:check`, `pnpm typecheck` (three tsconfig files, including `tsconfig.e2e.json`), and `pnpm build` also pass.

### End-to-end tests (`frontend/e2e/`, 5 spec files, 9 tests)

Written with Playwright Test and run with `pnpm test:e2e` from `frontend/`. The Playwright config (`frontend/playwright.config.ts`) does the following:

- `testDir` is `e2e`; the project is Chromium with `devices['Desktop Chrome']`; locally `E2E_BROWSER_CHANNEL=chrome` switches to the installed Google Chrome when the Chromium download is blocked; in CI (`CI` set) `forbidOnly` is on and each test gets one retry.
- `webServer` starts both servers: `uv run uvicorn app.main:app --host 127.0.0.1 --port 8013 --no-proxy-headers` from `../backend`, waited on through `/api/v1/health`, and `pnpm dev --port 5183 --strictPort` with `VITE_API_PROXY_TARGET=http://127.0.0.1:8013`, so the browser's `/api` calls go through the Vite proxy as in development. Both have a 120 s start timeout. Locally a server already listening on those ports is reused; in CI fresh ones are always started. The development ports 8000 and 5173 are never touched. `E2E_BASE_URL` and `E2E_API_PORT` override the two ports.
- The demo password is resolved once, before any server starts, by `e2e/support/env.ts`: `E2E_PASSWORD` when set (CI), otherwise `SEED_DEMO_PASSWORD` read from the repository `.env` (the value `app.seed --demo` used for the accounts). A missing value fails the run with a message naming both variables. Nothing is printed or committed.
- Traces are recorded with `trace: { mode: 'on-first-retry', sources: false }`: a trace exists only for a retried test and omits the spec sources, because the HTML report (`playwright-report/`, uploaded as a CI artifact on failure) would otherwise carry them. A trace still records typed values and request bodies, so the shared `signIn` helper in `e2e/support/auth.ts` never types the password: it posts `{username, password}` to `/api/v1/auth/login` with Node's `fetch`, outside the browser context, stores the returned token under `factory-sherlock.token` in `localStorage` through `page.evaluate`, loads `/`, and waits for the "Factory Overview" heading or the first `role="alert"`, failing with the alert's text so a wrong password or a throttled account is reported in one line. Only `login.spec.ts` types the password, through `signInThroughForm`, and that file runs under `test.use({ trace: 'off' })`. The short-lived bearer token is the only credential a trace can hold.
- `apiToken`, `apiGet`, and `bearer` in the same helper let specs read reference data through the API before driving the screen (the production day of CNC-03, the first consuming batch of a lot, a lot that is still AVAILABLE), so the specs do not hard-code dates or ids from the seed.

The five specs are described in TM-30 to TM-34. They assume the demo scenario (`database/seeds/demo_scenario.json`), run their files in parallel and their tests in order, and leave data behind (one closed investigation and one quarantined lot per run; after six runs `make reset-demo` is needed), as `frontend/e2e/README.md` documents. This pass did not run the suite and found by reading the code that `login.spec.ts` and `investigation.spec.ts` locate the sidebar as `getByRole('complementary', { name: 'Primary' })` while `Sidebar.tsx` now labels the `aside` "Sidebar" and the `nav` "Primary"; those two specs are expected to fail until the locator is changed to `getByRole('navigation', { name: 'Primary' })`.

## Test databases

`backend/app/core/config.py` computes `effective_database`: when `APP_ENV=test` the application, Alembic, and the reset script all use `<MYSQL_DATABASE>_test` (`factory_sherlock_test` with the default name). `scripts/setup/init_databases.sh` creates both schemas with identical grants for the application user, so the test suite can run migrations itself. `tests/conftest.py` sets `APP_ENV=test` before importing the application, and the session-scoped migration fixture asserts that the effective name ends with `_test` before running `alembic upgrade head`.

Isolation per test: the `db_session` fixture truncates every table in `Base.metadata.sorted_tables` (with `FOREIGN_KEY_CHECKS` off), re-applies `01_reference_data.sql`, and recreates the demo users with `TEST_PASSWORD`, so no test depends on another and no secret is read from the environment for the accounts. Unit tests never open a session. Because truncation is global to the schema, exactly one pytest process may use one `_test` schema at a time; two concurrent runs on the same schema truncate each other's data mid-test and fail in ways that look like application bugs. When several worktrees run the suite in parallel, each one gets its own `MYSQL_DATABASE` in its `.env` (during the 2026-11-07 integration run the worktrees used `fs_w01` to `fs_w20`, each with its `fs_wNN_test` sibling created by the setup script), and `alembic upgrade head` is run once per database before the first test run.

Running the backend tests:

```bash
cd backend
uv run alembic upgrade head                      # APP_ENV=test in .env, or let the fixture do it
uv run pytest                                    # unit + API + integration (make test-backend)
uv run pytest -m "not integration"               # unit only, no MySQL needed
uv run pytest --cov=app --cov-report=term-missing
uv run python ../scripts/development/reset_database.py   # with APP_ENV=test: drop and rebuild the test schema
```

Rules: tests never run with `APP_ENV=development` (the fixture refuses); the migration fixture, not a developer, is responsible for the schema being at head; API and integration tests must not run concurrently against the same test database; the process-wide login throttle is reset around every test; the two job tests re-enable the module logger that Alembic's `fileConfig` disables.

## Benchmarks

Two scripts under `scripts/development/` time persistence paths against the configured development database. Neither runs in CI or in the test suite; both roll their writes back (InnoDB auto-increment counters still advance) and report the median of three runs.

- `benchmark_simulation.py` (`make benchmark-sim`) times `simulation_service.run_simulation`, the function behind `POST /simulation/runs`, for the demo shape (3 machines x 12 batches x 20 units, 2 faults) and a large shape (3 x 40 x 50, 1 fault), and prints the median service time, the engine-only time, and rows per second (units plus inspections). Figures recorded in `docs/simulation/simulation-design.md` for the switch to chunked bulk inserts, local MySQL 8.4 on the same machine: demo shape (700 units, 1400 inspections) 0.29 s to 0.04 s (7266 to 57274 rows/s); large shape (6000 units, 12000 inspections) 1.71 s to 0.25 s (10517 to 72173 rows/s); the engine alone takes under 0.01 s and 0.03 s respectively. A second run agreed within 0.03 s.
- `benchmark_inspection_import.py` builds one STEEL-SHAFT batch of 2500 units (two specifications each, so 5000 rows, the import maximum), renders the CSV, counts SQL statements with a `before_cursor_execute` listener, and times `inspection_import.import_csv` inside a rolled-back savepoint. Figures recorded in `docs/quality/inspection-import.md` (development database `fs_w02`, 250 failing rows with an explicit code): one `record_inspection` call per row (before) 10507 statements, 1.47 s, 3396 rows/s; chunked bulk insert (now) 15 statements, 0.11 s, 46051 rows/s (45500 after the branch was rebased). The script times the service call only, without HTTP, multipart parsing, or JSON encoding.

The numbers are specific to the development machine and a local MySQL; a networked database would widen both gaps because the earlier paths issued one statement per row.

## Known gaps

- The Playwright suite has not been run since the frontend accessibility pass and the `signIn` rewrite of 2026-11-07, and no End-to-End or Compose Smoke workflow run has been observed. Two specs use a sidebar locator that no longer matches (see End-to-end tests). The suite also leaves data in the demo database and does not cover machine status changes, batch creation and completion, manual or CSV inspection entry, simulation runs, the overdue check, or alert acknowledgement in the browser.
- No test stops MySQL; the 503 path is produced by pointing the session factory at a closed port, which raises the same `OperationalError` 2003. Pool exhaustion is simulated with a constructed `TimeoutError`, not observed.
- The login throttle is per process. Behaviour with several uvicorn workers (each allowing `LOGIN_MAX_FAILURES` attempts) is documented in SECURITY.md and not tested.
- No response-time or throughput test exists for API endpoints. The two benchmark scripts are run by hand and their figures are recorded in documents, not asserted. EXPLAIN plans and index use are documented in `docs/database/database-design.md` and `docs/database/queries.md` and not asserted by a test.
- NFR-3.2 (two investigations on the same window produce the same evidence rows) has no dedicated test; determinism is covered for the simulation and for the rule arithmetic, not end to end for the investigation.
- Frontend: the Machines, Batches, Inspections, Investigations list and detail, and Simulation pages have component tests only for their shared parts (`BatchActions`, `EvidenceCard`, `ImportInspectionsPanel`, `StatTile`, charts); colour contrast (NFR-6.3), the 320 px layout (NFR-6.5), and screen reader output are checked by hand, not by a test. The contrast ratios computed during the 2026-11-07 accessibility pass are in that pass's report, not in the repository.
- `app/seed.py` as a command line (argument parsing, `--demo` from the shell), `scripts/development/reset_database.py`, `export_openapi.py`, and `export_schema.sh` are exercised by the setup guide and CI steps, not by tests.
- The CSV import's concurrency tests inject the competing write through a monkeypatched hook between validation and the bulk write; a true two-request race under load is not reproduced. The overdue check's concurrency test does use two real sessions and a thread.
