## 3. Decisions, alternatives, assumptions, constraints, and rationale

Normalization rationale. Every table has a single-column surrogate primary key except the three junction tables, which use the composite of their two foreign keys. Repeating groups are removed: specifications are rows of product_specifications, not columns on products; defects found by an inspection are rows of inspection_defects, not a delimited string. Partial dependencies are absent because each non-key column depends on the whole key, including in the junction tables (quantity_used depends on the batch and the lot together). Transitive dependencies are absent: machine name lives only on machines, product name only on products, and supplier only on material_lots. Two intentional, documented exceptions: inspections.result is stored rather than derived so historical results do not change when a tolerance is edited, and production_orders.quantity_completed is maintained by the service so order lists do not need an aggregate over batches.

| Decision | Alternatives considered | Rationale |
|---|---|---|
| Composite primary keys on junction tables | Surrogate id plus a UNIQUE pair | The pair is the identity; the composite key doubles as the index the traversal queries need |
| Delete behavior per foreign key: RESTRICT for history, CASCADE for owned rows, SET NULL for optional references | ON DELETE CASCADE everywhere | Deleting a machine with recorded batches would silently destroy production history |
| Five secondary indexes only | Index every foreign key column | Each index is justified by a query in database/queries; production_units.produced_at is left unindexed and documented as a follow-up for larger datasets |
| Investigation evidence stores the SQL text and the result rows as JSON (a columns list plus value arrays, because MySQL reorders JSON object keys) | Store only a rule code and recompute on view | The case board shows the exact query behind every finding, and rows keep their shape and column order per rule |
| Query results tied to a demo scenario with a fixed seed | Random data on every run | Results are reproducible for the defense and for tests |

Assumptions: the demo scenario covers one production day (06:00 to 12:00) on three machines; thresholds (elevated defect rate 5 percent and twice the fleet, batch review rate 10 percent, six hour event lookback) are documented in backend/app/investigation/rules.py and docs/investigation.

## 4. AI help: what, why, accepted, revised, rejected, and verification

Tool: Claude Code (Anthropic), used to draft the migration, the simulation engine, and query headers. The student ran migrations up and down, loaded the seed, and executed every query against MySQL 8.4 before keeping the code.

| Stage | Task | Recommendation | Decision | Verification |
|---|---|---|---|---|
| Migration | Alembic downgrade | The generated downgrade dropped the secondary indexes before dropping the tables | Rejected: MySQL refuses to drop an index that backs a foreign key while the constraint still exists, so the explicit index drops were removed and the indexes are dropped with their tables | Confirmed by running alembic downgrade base and alembic upgrade head against MySQL 8.4 |
| Simulation | End-of-run machine state | The first simulation engine moved a machine in WARNING straight to IDLE when the run finished | Revised: the shared state machine (domain/state_machines.py) rejected the transition because WARNING allows only RUNNING, STOPPED, or FAULT; the design was changed so a faulted machine stays in WARNING at the end of a run and only a healthy RUNNING machine returns to IDLE | Confirmed by running the demo scenario against MySQL 8.4: CNC-03 finishes in WARNING and CNC-01 in IDLE, so the unresolved fault remains visible in the machine status |

Lesson recorded: the state machine is one shared table of allowed transitions, so a transition that the simulator takes must also be legal for the API; letting the domain layer reject the generated code was the intended safety net.

## 5. Lessons learned at this milestone

- A composite index on (machine_id, occurred_at) or (inspected_at, result) serves several queries at once when the leading column matches the most selective filter.
- Writing the business question and expected shape in the query header before the SQL kept every query tied to a screen or rule and made results easy to check.
- MySQL-specific behavior (index and foreign key coupling, LATERAL support from 8.0.14, GROUPING() with ROLLUP) must be verified on the real server, not assumed from general SQL knowledge.
