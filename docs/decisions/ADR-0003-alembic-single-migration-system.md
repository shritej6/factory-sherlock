# ADR-0003: Alembic as the single schema migration system

## Status

Accepted. Recorded 2026-11-03. Implemented in `backend/alembic.ini`, `backend/migrations/`, and `scripts/development/export_schema.sh`.

## Context

Three artefacts could each claim to define the schema: the SQLAlchemy models in `backend/app/models`, a hand-written `schema.sql`, and migration scripts. Course deliverables usually include a readable DDL file, while the application needs a repeatable way to create and evolve the database on every developer machine and in the test database. Having two authoritative sources invites drift.

## Decision

Alembic is the only authority for schema changes:

- `backend/migrations/versions/` holds the migration chain. The current chain is a single revision (`3a5e982c3679`, "create manufacturing schema") that creates all 17 tables with their constraints and indexes.
- `backend/migrations/env.py` imports `app.models` so that `Base.metadata` carries every table, and reads the connection URL from `app.core.config.get_settings()`. Migrations therefore run against the same database the application uses, including the `_test` schema when `APP_ENV=test`. No credentials appear in `alembic.ini`.
- `database/schema/schema.sql` is a generated snapshot produced by `scripts/development/export_schema.sh` (`mysqldump --no-data`) from a migrated database. Its header says "Do not edit by hand"; it exists so the DDL can be read without running the application.
- `scripts/development/reset_database.py` drops every table and re-runs `alembic upgrade head` followed by the seed command; it never bypasses Alembic.
- Future schema changes are new revisions. `env.py` configures `compare_type=True` so autogenerate detects type changes.

## Consequences

Positive:

- One command (`uv run alembic upgrade head`) creates the schema on a fresh database, in CI, and in the test database.
- The ORM models, the migration, and the exported DDL agree because the migration was generated from the models and the DDL is dumped from the migrated database.
- Reviewers can read `schema.sql` as a plain file while developers keep a reversible history.

Negative or accepted costs:

- The exported `schema.sql` can go stale if someone forgets to re-run the export after a migration. The header and this ADR make the direction of truth explicit; a CI check that regenerates and diffs the file is a planned follow-up.
- Autogenerated migrations need manual review. The initial revision carries a note in `downgrade()` explaining why indexes are not dropped separately (MySQL refuses to drop an index that backs a foreign key while the constraint exists).
- Alembic's `alembic_version` table is the 18th table in the database; documentation counts 17 application tables.
- Data migrations (for example backfilling a column) must be written by hand in revision scripts; the seed file is for reference data only.

## Alternatives considered

- Hand-maintained `schema.sql` applied with the `mysql` client. Rejected: no versioning, no reversible steps, and the ORM models would have to be kept in sync by hand.
- `Base.metadata.create_all()` at application start. Rejected: cannot evolve an existing schema, and silently creates tables in whatever database the application is pointed at.
- Both Alembic and a hand-written DDL as co-equal sources. Rejected: this is the drift scenario the decision exists to prevent. The DDL file is kept, but as an export.
